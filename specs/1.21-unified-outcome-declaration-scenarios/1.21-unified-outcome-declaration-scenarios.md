## Problem
Two gaps share one root cause: the spec states outcomes in prose, so nothing downstream can address them.

1. **The AC-to-proof mapping is re-derived three times.** `authoring.md:94` gives `- [ ] <criterion> — <how proven>` as free text, so `flow-verifier.md:20`, `skills/pr/reference/spec.md:9`, and `skills/pr/reference/tests.md:9` each independently guess which test covers which criterion. Three agents, three guesses, one mapping the spec author already knew.
2. **The one machine-readable outcome the toolkit has excludes most of its projects.** `implement.md:41`'s `validate.intent` — "a new user buys one item and reaches confirmation" — is a Gherkin scenario title in all but syntax, but it binds solely to `flow-ux-validator`, which returns `NOT APPLICABLE` for backend, CLI, and infra repos. This repo is bash + markdown and can never use its own mechanism.

The toolkit asserts test-first in eight places (`SKILL.md:88`, `implement.md:19`, `flow-implementer.md:3`, both dev-cycle diagrams) and operationalizes it in none — compare deferrals, which get a schema, a preflight command, a commit-guard block, and lint + ship checks.

Shipped means: one declarative outcome block in front-matter, each entry naming the proof that settles it, routed to whichever executor fits the project — with the outer scenario failing before the first implementation commit.

## Value
As an engineer running flow I want each acceptance criterion to name the scenario and the command that proves it so that the verifier and both PR reviewers read one mapping instead of inferring three, and so that test-first is something the toolkit checks rather than something it says.

## Scope
**In:** a stack-neutral `scenarios:` front-matter block (Given/When/Then text, the proof that settles it, and which criterion it covers); generalizing `validate:` so `intent` becomes one scenario kind rather than the only one; executor routing — drivable UI to `flow-ux-validator`, everything else to the named test/command; outside-in ordering in `implement.md` section 3 (outer scenario red before the first implementation commit); `flow-verifier` and `skills/pr/reference/{spec,tests}.md` reading the declared mapping instead of guessing; conversational scenario elicitation (example mapping) in `--add` and `implement.md` section 2; `flow-preflight.sh` resolution plus a `/flow:lint` check; docs.

**Out:** a BDD runner, `.feature` files, step definitions, or any per-stack test dependency — the toolkit has zero runtime dependencies and must stay stack-agnostic (see Decisions). Generating real feature files for stacks that want them is a later spec, gated on this one proving out. Rewriting archived specs — per the standing rule, new conventions apply to new specs only.

## Decisions
- 2026-08-17 — **Gherkin as declaration, not as apparatus.** Adopting Cucumber/behave/SpecFlow/pytest-bdd would make the toolkit stack-specific; it currently has zero runtime dependencies and the README positions it as working in any project (.NET, Node, Python, whatever). The scenario text lives in the spec; the implementer translates it to whatever the target project's `CLAUDE.md` names as its test framework. That is the thin slice; a real runner is a second spec if a second real use appears.
- 2026-08-17 — **One declaration, two executors.** `validate.intent` and a test-backed scenario are the same statement — an outcome — differing only in what runs them. Shipping them separately would leave the toolkit with two overlapping outcome vocabularies and break its own rule that a rule lives in exactly one place. `validate:` is absorbed as one scenario kind and stays permanently valid, following the `<id>.md` / `<id>-<slug>.md` precedent.
- 2026-08-17 — **The proof pointer is the whole point.** The value is not Gherkin phrasing; it is that `proves:` plus `by:` turn a mapping three agents currently guess into one the spec states once.
- 2026-08-17 — **Sequenced after 1.20.** The spec reviewer's SMART/Measurable finding — a criterion that names no proof — is exactly the demand signal for this block, and it will show which shape the block actually needs before the format is fixed.
- 2026-08-17 — **Elicitation is an AC here, not its own spec.** `SKILL.md:95` already mandates propose-and-confirm; `--add` and section 2 are already elicit-then-confirm flows. A standalone interactive mode would add a fourth entry point into spec authoring alongside `--add`, section 2, and `--condense`, for behavior those paths already exhibit.
- 2026-08-17 — **Uncovered criteria warn, never block.** A hard gate would make every existing spec in every downstream project instantly non-compliant. Adoption is per-spec and opt-in, like `validate:`.
