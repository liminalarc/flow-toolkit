## Goal
Define the front-matter format and make it machine-resolvable. The block is declarative text plus two pointers — no runner, no new file type.

```yaml
scenarios:
  - given: "a repo with no .flow/config.yml"
    when: "the engineer runs /flow:run"
    then: "the local backend is assumed and the index is read from SPECIFICATIONS.md"
    proves: AC2                      # which acceptance criterion this settles
    by: "bash hooks/hooks.test.sh"   # the command that runs it, or `ux-validator`
```

- **`given`/`when`/`then`** — plain sentences. Gherkin's shape, not its tooling.
- **`proves:`** — the acceptance criterion this settles, addressed by position (`AC1`, `AC2`, …) against the `## Acceptance criteria` list. Positional keeps the spec terse and needs no ids sprinkled through the AC lines.
- **`by:`** — the command that settles it, or the literal `ux-validator` to route to the live-app executor (T2).

Extend `flow-preflight.sh` with a `scenarios <spec.md> [--repo DIR]` subcommand: parse the block, validate each entry has all five keys, and confirm every `proves:` resolves to a real criterion in that spec. Follow the file's existing pragmatic front-matter parsing — the same approach `cmd_resolved` uses for `deferrals:`. Absent block exits 0 silently.

`flow-spec-guard.sh` gains no allowlist change (it does not gate front-matter keys, which is why `validate:` needed no guard edit in 1.15) but does call `scenarios` when the block is present, so a malformed block fails on save rather than at build time.

`/flow:lint --specs` gains one row: a criterion with no scenario covering it → **WARNING**. Never an ERROR — adoption is opt-in per spec.

## Done when
- [ ] `flow-preflight.sh scenarios <spec>` validates key presence and `proves:` resolution, exits 0 silently on a spec with no block, and returns a non-zero with a specific message on a malformed one.
- [ ] `hooks/hooks.test.sh` covers: well-formed block, missing key, `proves:` pointing past the end of the AC list, absent block. All green.
- [ ] `flow-spec-guard.sh` rejects a malformed block on save and is silent when the block is absent — proven by saving one spec of each kind.
- [ ] `/flow:lint --specs` reports an uncovered criterion as WARNING and never as ERROR.
- [ ] `authoring.md` documents the block in the detail-file template as a commented-out optional section, matching how `validate:` is presented today.

## Notes
Positional `AC<n>` addressing has a known cost: reordering the AC list silently re-points every `proves:`. The lint check catches an out-of-range pointer but not a re-aimed one. Accepted for the thin slice — named criterion ids are the fallback if it bites.
