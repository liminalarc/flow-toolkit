## Problem
A spec whose deliverable is *an ordered group of other specs* has nowhere to record the ordering. Spec 1.2 did exactly this — its acceptance criterion reads "Implementation specs spawned (1.6–1.11) for each independently-shippable piece" — and the resulting dependency graph became a prose table in `docs/architecture.md` (`| id | Covers | Depends on |`), carrying a parallel branch and a non-linear edge that no check can read. Two rules already depend on data that does not exist: `skills/run/SKILL.md`'s "If the work depends on an unfinished spec, stop and say so", and spec 1.20's INVEST **Independent** test ("Can this ship without unfinished work landing first?"), which today answers from prose or not at all.

Shipped means: an orchestrating spec declares its group's order in front-matter, that declaration is machine-validated, and the spec-review gate answers *Independent* from it.

## Value
As an engineer running a multi-spec plan I want the order recorded and checked in one place so that I never start a spec whose prerequisite is unbuilt, and never re-derive the sequence from a prose table that drifts from the backlog.

## Scope
**In:** a `spawns:` front-matter key on the orchestrating spec — a list of `{id, after}` entries, mirroring the `deferrals:` shape. **`after` is a scalar**, read as text and split on `[`, `]`, `,`, and whitespace, so `after: []`, `after: [1.6]`, `after: [1.6, 1.8]`, and bare `after: 1.6` all parse without touching `parse_deferrals`'s entry detection. Two preflight subcommands: `spawns <spec>` (validate shape, id resolution, acyclicity) and `blocking <id>` (**the reverse lookup** — given a member id, report the unmet `after` ids from whichever spawn set owns it). Both take the DONE set the same way `resolved` does. A `flow-spec-guard.sh` call when the key is present, a `/flow:lint --specs` row, and the Independent letter of the spec-review gate answering from `blocking` — **run by the orchestrator at `implement.md` §2 and passed into the dispatch**, not by the agent. Docs.

**Out:** every ordering *consumer* — a repo-wide `next` query, `/flow:run` no-args ordering, and a session-brief blocked count — deferred to a follow-up spec gated on a live spawn set (see Decisions; the brief consumer is additionally local-only, since `flow-session-brief.sh` has no spec data in `ado` mode). Backfilling `spawns:` into archived spec 1.2 or any other closed work. Granting `flow-spec-reviewer` a `Bash` tool. Reading or writing ADO predecessor/successor link types. A separate `plans/` artifact or a `plan:` grouping label — no second real use yet.

## Acceptance criteria
- [ ] A `spawns:` block of `{id, after}` entries parses, with `after` as a scalar split on `[`, `]`, `,` and whitespace — proven by `hooks/hooks.test.sh` cases covering `after: []`, `after: [1.6]`, `after: [1.6, 1.8]`, and bare `after: 1.6`, each yielding the expected id set.
- [ ] `flow-preflight.sh spawns <spec>` exits non-zero naming the offending entry when it lacks `id` — proven by a harness case.
- [ ] It exits non-zero naming the offending entry when it lacks `after` — proven by a harness case.
- [ ] It exits non-zero naming the id when a spawned `id` has no detail file — proven by a harness case.
- [ ] It exits non-zero naming an `after` id that resolves to no detail file, on the same rule as a spawned `id` — proven by a harness case, so a typo cannot become a silent permanent blocker.
- [ ] It exits non-zero naming every id in the cycle when the graph is cyclic — proven by a harness case fixturing `A after B`, `B after A`.
- [ ] `spawns` and `blocking` obtain the DONE set exactly as `resolved` does — `--done <ids>` wins, else the local index, else a non-silent "cannot determine" — proven by three harness cases, one per branch, asserting the same exit-code contract `cmd_resolved` uses.
- [ ] An `after` naming a *resolvable* id outside the spawn set is a **blocker, not an error** — proven by a harness case where a cross-set `after` on a `NOT STARTED` id yields that id from `blocking` and exit 0 from `spawns`.
- [ ] `flow-preflight.sh blocking <id>` prints the unmet `after` ids for a member of a partially-built set, prints nothing and exits 0 for an unblocked member, and prints nothing and exits 0 for an id in no spawn set — proven by three harness cases over one fixture with a partially-built graph.
- [ ] `blocking` resolves a spawn set whose orchestrator is archived — proven by a harness case with the orchestrator under `specs/archive/`.
- [ ] A spawning spec reaches `DONE` while its members are still open — proven by a harness case asserting `resolved` stays clean for a `DONE` spec with open `spawns:` entries (the 1.2 shape must not regress).
- [ ] A detail file carrying **both** `spawns:` and `deferrals:` yields the same parsed deferral entries and the same session-brief line as one carrying `deferrals:` alone — proven by `hooks/hooks.test.sh` cases asserting both, on fixtures with the keys in **either order**.
- [ ] `flow-spec-guard.sh` rejects a malformed `spawns:` block on save and is silent when the key is absent — proven by two harness cases.
- [ ] The `/flow:lint --specs` row fires only when `spawns:` is present — proven by inspection of the row's stated guard condition (`/flow:lint` is a model-executed prompt, so there is no bash-capturable output to diff).
- [ ] `implement.md` §2 runs `flow-preflight.sh blocking <id>` and passes any unmet ids into the `flow-spec-reviewer` dispatch, and the rubric directs the Independent letter to use them — proven by inspection of the `implement.md` and `spec-review.md` edits plus a stand-in dispatch on a member of a partially-built set returning Independent WEAK citing the unmet id. (Name-dispatch verified after `/plugin update`, per 1.20's precedent.)

## Decisions
- 2026-09-01 — **`spawns:` records and orders; it never gates `DONE`.** The obvious design — a spawning spec cannot close until its members do — is disproven by the case that motivated this spec: 1.2's Verification defines shipped as "ratified decisions + a spawned, well-formed backlog", and it correctly reached `DONE` long before 1.6–1.11 were built. Gating would have blocked it wrongly.
- 2026-09-01 — **Ship the declaration; defer every consumer.** The first draft bundled the format, a repo-wide `next` query, and three consumer wirings. Spec review returned `BLOCKING: yes` on Small, and its end-to-end proof was unfalsifiable here: this repo's only spawn set is 1.2's, whose six members are all `DONE`, so no consumer would have live blocked work to act on.
- 2026-09-01 — **`blocking <id>` (reverse lookup) is in scope, and is what makes the review gate work.** `after` lives on the *orchestrator*, so a reviewer judging member X cannot see X's blockers without a member→owning-set query.
- 2026-09-01 — **The orchestrator runs `blocking`; the reviewer stays shell-free.** `flow-spec-reviewer` declares `tools: Read, Grep, Glob` — it has no `Bash` and cannot execute a preflight subcommand, so wiring the Independent letter to "call `blocking`" would have been unbuildable. Granting it `Bash` was the alternative (the verifier, pr-reviewer, and ux-validator all have it), but 1.20 deliberately kept this judge a pure reader, and `implement.md` §2 already locates and calls `flow-preflight.sh` for `autonomy` and `spec-path`. So the orchestrator resolves the blockers and passes them in, exactly as it already passes the rubric path, project root, and archive location.
- 2026-09-01 — **`after` is a scalar, not a nested sequence.** `parse_deferrals` treats any line matching `^[[:space:]]*-[[:space:]]` inside the block as a **new entry**, so a nested YAML list under `after:` would be misparsed as extra spawn entries. Reading the value as text and splitting on `[`, `]`, `,` and whitespace keeps the inline-list spelling readable while leaving the existing parser untouched — and matches how `--done` already takes a space-separated id list.
- 2026-09-01 — **An unresolvable `after` id is an error, not a blocker.** A cross-set `after` that names a *real* spec is a legitimate blocker (forbidding it would rule out the very cross-spec dependency `SKILL.md`'s existing rule describes), but one that resolves to nothing is a typo, and treating it as a blocker would stall a member forever with no signal. It errors on the same rule as a spawned `id`.
- 2026-09-01 — **The DONE set is an input, never a guess.** `cmd_resolved` already settled this: `--done` wins (ado / caller-supplied), else the local index, else "cannot determine — never a silent pass." Both new subcommands mirror it rather than inventing a second rule.
- 2026-09-01 — **No backfill of archived specs; 1.2's table stays where it is.** Retrofitting closed work is against standing practice here — 1.18 put "retro-moving anything in an existing repo" out of scope, and 1.17 made its retrofit a separate, opt-in `/flow:lint --rename`. Evidence comes from purpose-built harness fixtures instead, which is also the only way to fixture a *partially-built* graph.
- 2026-09-01 — **Validating a declared key is not the shape enforcement 1.2's D1 ruled out.** D1 declined to enforce the *breakout threshold* before drift appeared. This validates the well-formedness of a key the author chose to write — the `deferrals:`/`wellformed` precedent — not a judgment about how a spec should be structured. A spec with no `spawns:` key is untouched.
- 2026-09-01 — **Day-one user is a live spawn set in another flow project**, not this repo. That set — not 1.2's closed one — is the real acceptance test after ship.

- 2026-09-02 — **AC12 re-aimed at a regression that can actually happen.** It originally asserted the session brief stayed byte-identical when `spawns:` is absent, "proven by diffing against the pre-change build". Two faults, caught at the §2 gate: `hooks.test.sh` runs only the current tree (`hooks/hooks.test.sh:844` invokes `$BRIEF` and asserts literal text), so no such diff exists; and the session-brief consumer is explicitly Out of scope, so the assertion could not fail under any implementation. It now targets the real interaction — `spawns:` is a front-matter sibling of `deferrals:` whose entries are also `- ` lines, and `flow-preflight.sh:101` is where the deferrals parser decides a new top-level key ended its list.

## Verification / evidence
Each criterion names its harness case. Evidence comes from purpose-built fixtures in `hooks/hooks.test.sh`, including one partially-built graph (some members `DONE`, some open) that this repo cannot supply, since its only spawn set is fully closed. `bash hooks/hooks.test.sh` green is the gate. Post-ship, the live spawn set in the other project is the real-world check.

**Coordination, not dependency:** in-flight 1.21 adds a `scenarios` preflight subcommand, a spec-guard call, and a `/flow:lint --specs` row in the same three regions this spec edits. Parallel work on the same files — sequence them or expect a merge.
