## Problem
Three consumers need the same two answers. The banner (1.26) needs a work item's footprint, where each sibling slice should live, and whether it is done; the terminal gate (1.27) needs that same completion answer in both backends; the lint drift row (1.28) needs the same footprint comparison to spot a stale card tag. Drafted separately, each would carry its own copy — and 1.26, ordered before 1.27, would have built a prompt-prose reader that 1.27 replaced in bash. Root CLAUDE.md settles it: a machine-checkable invariant belongs in `flow-preflight.sh` and is never re-implemented inline.

Shipped means: both answers come from one place, with harness cases, and every consumer calls it.

## Value
As an engineer building the cross-repo consumers I want every footprint and status answer behind one tested pair of subcommands so that three prompts cannot drift into three slightly different definitions of the same question.

## Scope
**In:** two read-only `flow-preflight.sh` subcommands. Both need the footprint keys 1.25 declared, so **extending 1.25's config parser is in scope**: `parse_related` gains a **fourth** `US` field carrying `key=value` pairs (`clone=`, `local_path=`), leaving fields 1-3 byte-identical so shipped `cmd_repos` is untouched. `local_path` is merged in from `.flow/config.local.yml`, matched to a sibling by `name`; that file supplies `local_path` and nothing else. The membership set `cmd_repos` computes inline (`repo_name` ∪ `related_repos` names) is extracted to a shared helper and called by both, so the rule lives in one place.

`resolve-footprint [<spec>] [--tags "repo:a repo:b"] [--repo DIR]` — `<spec>` is **optional**, because the case tags exist for (ado first-open in a repo with no slice file yet) has no spec to pass. Output, one fact per line:

```
this: <repo_name>                         # which record is this repo
source: front-matter | tags
repo: <name> | clone: <url|-> | local_path: <path|-> | slice: <path|dir|->
divergence: +<added>... -<omitted>...     # only when both sources exist and differ
undeclared: <name>                        # per name in neither repo_name nor related_repos
undeclared-self:                          # flow.repo_name unset
```

`slice:` is the **found** slice path when the `work_item:` lookup resolves one, else the sibling's **spec directory** (where it would land — the filename is unpredictable, since 1.24 D2 gives the sibling its own id), else `-` when `local_path` is unknown. `divergence:` is one line carrying every token, adds before omits, each group sorted. Front-matter wins wherever a local `repos:` exists; tags are read only where it does not.

`slice-status [<spec>] [--slice-done "slice-done:a"] [--repo DIR]` — per repo, one of `done` | `open` | `absent` | `cannot-determine`. **The branch is chosen by the flag**: `--slice-done` present ⇒ ado (completion from the tags 1.27 writes); absent ⇒ flat-file. Presence is tracked by a seen-flag, not by emptiness, so `--slice-done ""` is an ado run with no tags, not a flat-file run.

Flat-file resolution is three steps, because a sibling's index records the **sibling's own ids**, never `work_item:`: find the sibling detail file whose `work_item:` matches (default `work_item:` = `id:`; `specs/archive/` included), take *its* `id:`, then read that id's status from the sibling's index. The five-value index vocabulary maps to four: `DONE` and `SUPERSEDED` → `done` (both terminal — a `SUPERSEDED` slice no longer owns work, and reading it as `open` would block a work item forever); `NOT STARTED`, `IN PROGRESS`, `PARTIAL` → `open`. `absent` means reachable, flow-managed, and no file matches the handle. `cannot-determine` covers: `local_path` missing, unreadable, or not flow-managed (no `.flow/` and no `SPECIFICATIONS.md`); the sibling has **no index at all** (an ado-backed sibling); a file matches but its `id:` has **no entry** in the sibling's index; and two files match one handle.

**Board data is an input, never a query** — `--tags`/`--slice-done` mirror `resolved --done`. Neither subcommand contains a network or `az` call on any path, which is what makes the whole spec provable offline. Exit 0 always; indeterminacy rides in the per-repo value, never the exit code. Harness cases. Docs.

**Out:** every consumer — the banner (1.26), the gate (1.27), the drift row and `--fix` (1.28). Writing anything, anywhere. Fetching `clone`. Querying a board. Changing `cmd_repos`'s behavior or its three existing `parse_related` fields. Deciding what a consumer *does* with `absent`, `cannot-determine` or `undeclared:` — those contracts belong to 1.26/1.27/1.28.

## Acceptance criteria
- [ ] `resolve-footprint <spec>` emits one `repo:` line per footprint name carrying all four fields, with `source: front-matter`, when a local slice file exists — proven by a harness case asserting each field's value, so 1.26 renders its banner without reading config itself.
- [ ] A `this: <repo_name>` line names which record is this repo — proven by a harness case. 1.26's Scope forbids it reading config, so without this it cannot tell its own slice from a sibling's and would have to re-derive `repo_name` itself.
- [ ] `slice:` holds the found slice path when the `work_item:` lookup resolves one, the sibling's spec **directory** when it does not, and `-` when `local_path` is unknown — proven by three harness cases, one per branch. The filename is unpredictable by design (1.24 D2 gives the sibling its own id), so the directory is the honest answer, not a guessed path.
- [ ] `local_path` is merged from `.flow/config.local.yml` by sibling `name`, and that file supplies nothing else — proven by a harness case whose override also sets `clone`, asserting the committed `clone` wins and the override's is ignored.
- [ ] `resolve-footprint --tags "repo:a repo:b"` with **no `<spec>` argument** returns that set and reports `source: tags` — proven by a harness case, which is the ado first-open case where no spec file exists to pass.
- [ ] Where a local `repos:` and `--tags` both exist and differ, it returns the **front-matter** set and emits one `divergence:` line carrying every token, adds before omits, each group sorted — proven by a harness case over a three-repo divergence asserting the literal line, so 1.26's banner and 1.28's `--fix` parse one agreed form at any size.
- [ ] Neither subcommand contains a network or `az` invocation on any code path — proven by `grep -nE '(^|[^a-z])(az|curl|wget|git (fetch|ls-remote|clone))'` over both function bodies returning nothing.
- [ ] `slice-status` chooses its branch by flag presence, tracked by a seen-flag rather than emptiness — `--slice-done ""` is an ado run with no tags, not a flat-file run — proven by two harness cases whose results differ only by whether the flag was passed.
- [ ] Flat-file status resolves through the three-step `work_item:` lookup, not by assuming the sibling shares this repo's id — proven by a harness case whose sibling uses this repo's id for an **unrelated** spec and carries the real slice under a different id, asserting the status of the right one.
- [ ] The five-value index vocabulary maps to four: `DONE` and `SUPERSEDED` yield `done`; `NOT STARTED`, `IN PROGRESS` and `PARTIAL` yield `open` — proven by five harness cases, one per index status, so `SUPERSEDED` can neither block a work item forever nor pass silently unexamined.
- [ ] `absent` is returned only for a reachable, flow-managed sibling with no file matching the handle — proven by a harness case, distinguishing "not authored yet" from "cannot tell".
- [ ] `cannot-determine` covers every other unknown — `local_path` missing, unreadable, or not flow-managed (no `.flow/` and no `SPECIFICATIONS.md`); the sibling having no index at all; a matching file whose `id:` has no index entry; and two files matching one handle, naming both paths — proven by six harness cases, one per condition.
- [ ] Ado status resolves from `--slice-done`, yielding `done` for a tagged repo and `open` for an untagged one in the footprint — proven by two harness cases.
- [ ] A mixed result exits 0 with one line per repo — proven by a harness case over a fixture with one `done` and one `cannot-determine`, asserting both lines and exit 0, so per-repo state never collapses into a process-wide exit code the way `resolved`'s does.
- [ ] `undeclared:` fires per footprint name absent from **both** `flow.repo_name` and `flow.related_repos`, reusing the same membership helper `cmd_repos` calls — proven by a harness case asserting this repo's own declared name does **not** appear, so an ordinary footprint emits none.
- [ ] `undeclared-self:` fires when `flow.repo_name` is unset — proven by a harness case on a config with `related_repos` and no `repo_name`.
- [ ] `undeclared` is reported, never enforced — the subcommand still exits 0 and still returns the resolved set — proven by a harness case asserting both, so a consumer chooses whether to warn, offer, or ignore.
- [ ] Both subcommands exit 0 and emit nothing when there is **no footprint from any source** — no `repos:` key *and* no `--tags` — proven by a harness case, so an unrelated project pays nothing and the cheap-exit cannot break the tags path.
- [ ] `cmd_repos` behaves identically after the `parse_related` extension — proven by the 1.25 cases still passing unchanged, since the new data rides in a fourth field and the first three are byte-identical.
- [ ] Neither writes to any tree — proven by a harness case asserting `git status` unchanged in both the fixture repo and its sibling after running each.
- [ ] Every documentation surface is updated in the same change — root `CLAUDE.md`'s `flow-preflight.sh` bullet, `hooks/CLAUDE.md`'s subcommand list, and `docs/guide.md` §5 — proven by `grep -l 'resolve-footprint'` and `grep -l 'slice-status'` over those three paths, each returning all three.

## Decisions
- 2026-09-24 — **Board data is an input, never a query.** 1.22 settled this for the DONE set — "`--done <ids>` wins, else the local index, else a non-silent cannot-determine", the helper never queries — and the same reasoning applies harder here: the spec guard calls preflight on every save, so a board round-trip behind it would put auth, latency and a failure mode on a hot path. `--tags`/`--slice-done` keep the whole spec offline-provable and let every consumer's ado criteria run against fed input rather than a live board. (`cmd_git_state`'s opt-out `--no-fetch` shows preflight *may* touch the network, but only behind a declared flag; nothing here needs that.)
- 2026-09-24 — **Four-way status, not three.** A reachable sibling whose slice simply has not been authored yet is neither `open` (nothing exists to be open) nor `cannot-determine` (the answer is known). It is `absent` — which is also exactly the found/not-found datum 1.26's banner would otherwise have derived in prose, so one vocabulary serves both consumers.
- 2026-09-24 — **Indeterminacy rides in the value, never the exit code.** `cmd_resolved` carries "cannot determine" as exit 2 because it answers one question about one run. These answer per repo, so a fixture with one `done` and one `cannot-determine` has no coherent process-wide code. Exit 0 always; the consumer reads the per-repo token. The "never a silent pass" contract is preserved by the token being explicit, not by the exit status.
- 2026-09-25 — **The record says which repo is this one** (amended at build time). Seeing real output made it obvious: every `repo:` line looked alike, but 1.26 must say "this run builds the *toolkit* slice" and its Scope bars it from reading config. Without a `this:` line it would have to re-derive `repo_name` — a second reader of 1.25's config, which is the duplication 1.29 exists to prevent. One line, emitted once.
- 2026-09-25 — **Undeclared repos are a report, not an error.** 1.25's `repos` already *blocks* a save when a spec's own front-matter names an undeclared repo — that is a local authoring mistake with a local fix. This is the other direction: a footprint arriving from card tags in a repo whose config predates cross-repo, where nothing is wrong with the spec and the fix is a config the human has not been asked for yet. Blocking there would punish a repo for being old. So it reports, and 1.28 does the asking.
- 2026-09-24 — **The resolvers report; they never decide.** `resolve-footprint` reports a divergence rather than repairing it; `slice-status` reports `absent`/`cannot-determine` rather than choosing an outcome. What to do about either belongs to a consumer — the `--fix` is 1.28's, the terminal disposition is 1.27's. That is what lets one pair of subcommands serve three consumers without encoding any one's policy.
- 2026-09-24 — **The front-matter parse is 1.25's, reused.** `repos:`/`work_item:`/`canonical_repo:` are declared and validated by 1.25; this spec calls that parser rather than writing a second one, per root CLAUDE.md's rule against re-implementing a check.
