## Problem
Three consumers need the same two answers. The banner (1.26) needs a work item's footprint, where each sibling slice should live, and whether it is done; the terminal gate (1.27) needs that same completion answer in both backends; the lint drift row (1.28) needs the same footprint comparison to spot a stale card tag. Drafted separately, each would carry its own copy — and 1.26, ordered before 1.27, would have built a prompt-prose reader that 1.27 replaced in bash. Root CLAUDE.md settles it: a machine-checkable invariant belongs in `flow-preflight.sh` and is never re-implemented inline.

Shipped means: both answers come from one place, with harness cases, and every consumer calls it.

## Value
As an engineer building the cross-repo consumers I want every footprint and status answer behind one tested pair of subcommands so that three prompts cannot drift into three slightly different definitions of the same question.

## Scope
**In:** two read-only `flow-preflight.sh` subcommands, both parsing the front-matter keys **1.25 owns** (`repos:`, `work_item:`, `canonical_repo:`) and reusing its parser rather than a second copy.

`resolve-footprint <spec>` — per repo in the footprint, one stdout record carrying `name`, its declared `clone`, its `local_path` (from the gitignored `.flow/config.local.yml`, per 1.25), and the **expected slice path** in that sibling; plus the set's `source:` (`front-matter` | `tags`) and, when both exist and differ, one `divergence: +<repo> -<repo>` line. Front-matter wins, per 1.24.

`slice-status <spec>` — per repo, one of four values: `done` | `open` | `absent` (reachable, flow-managed, no slice authored for this work item) | `cannot-determine`. Flat-file resolution is a three-step lookup, because a sibling's index records the **sibling's own ids**, never `work_item:`: find the sibling detail file whose `work_item:` matches (including the default `work_item:` = `id:`, and `specs/archive/`), take *its* `id:`, then read that id's status from the sibling's index. Ado resolution reads the `slice-done:<name>` tags 1.27 writes.

**Board data is an input, never a query** — `--tags` supplies `repo:` tags and `--slice-done` supplies completion tags, exactly as `resolved --done` supplies the DONE set. Neither subcommand contains a network or `az` call on any path, which is what makes the whole spec provable offline. Exit 0 always; indeterminacy rides in the per-repo value, never the exit code. Harness cases. Docs.

**Out:** every consumer — the banner (1.26), the gate (1.27), the drift row and `--fix` (1.28). Writing anything, anywhere. Fetching `clone`. Querying a board. Deciding what a consumer *does* with `absent` or `cannot-determine` — 1.26 and 1.27 own those contracts.

## Acceptance criteria
- [ ] `resolve-footprint` returns one record per repo carrying `name`, `clone`, `local_path` and the expected slice path, and reports `source: front-matter`, when a local slice file exists — proven by a `hooks/hooks.test.sh` case asserting all four fields and the source token, so 1.26 renders its banner without reading config itself.
- [ ] Given `--tags "repo:a repo:b"` and no local slice file, it returns that set and reports `source: tags` — proven by a harness case. The flag mirrors `resolved --done`, the precedent 1.22 set for getting board-derived data into a preflight subcommand.
- [ ] With both present and differing, it returns the **front-matter** set and emits exactly one `divergence: +<repo> -<repo>` line naming what the tags add and omit — proven by a harness case asserting the literal line, so 1.26's banner and 1.28's `--fix` parse one agreed form.
- [ ] Neither subcommand contains a network or `az` invocation on any code path — proven by `grep -nE '(^|[^a-z])(az|curl|wget|git (fetch|ls-remote|clone))' ` over both functions returning nothing.
- [ ] `slice-status` resolves flat-file status through the `work_item:` lookup, not by assuming the sibling shares this repo's id — proven by a harness case whose sibling uses this repo's id for an **unrelated** spec and carries the real slice under a different id, asserting the status of the right one.
- [ ] It reports `done` / `open` correctly, `absent` for a reachable flow-managed sibling with no slice for this work item, and `cannot-determine` when `local_path` is missing, unreadable, or names a non-flow directory — proven by six harness cases, one per outcome and one per `cannot-determine` condition.
- [ ] Two sibling files matching the same `work_item:` yield `cannot-determine` naming both paths, never an arbitrary pick — proven by a harness case.
- [ ] Ado status resolves from `--slice-done "slice-done:a"`, yielding `done` for a tagged repo and `open` for an untagged one in the footprint; absent input yields `cannot-determine`, never `open` — proven by three harness cases. This is the answer 1.27's ado gate consumes.
- [ ] A mixed result exits 0 with one line per repo — proven by a harness case over a fixture with one `done` and one `cannot-determine`, asserting both lines and exit 0, so per-repo state never collapses into a process-wide exit code the way `resolved`'s does.
- [ ] Both subcommands exit 0 and emit nothing for a spec with no `repos:` — proven by a harness case, so an unrelated project pays nothing.
- [ ] Neither writes to any tree — proven by a harness case asserting `git status` unchanged in both the fixture repo and its sibling after running each.
- [ ] Every documentation surface is updated in the same change — root `CLAUDE.md`'s `flow-preflight.sh` bullet, `hooks/CLAUDE.md`'s subcommand conventions, and `docs/guide.md` §5 — proven by `grep -l 'resolve-footprint' CLAUDE.md hooks/CLAUDE.md docs/guide.md` **and** the same for `slice-status`, each returning all three.

## Decisions
- 2026-09-24 — **Board data is an input, never a query.** 1.22 settled this for the DONE set — "`--done <ids>` wins, else the local index, else a non-silent cannot-determine", the helper never queries — and the same reasoning applies harder here: the spec guard calls preflight on every save, so a board round-trip behind it would put auth, latency and a failure mode on a hot path. `--tags`/`--slice-done` keep the whole spec offline-provable and let every consumer's ado criteria run against fed input rather than a live board. (`cmd_git_state`'s opt-out `--no-fetch` shows preflight *may* touch the network, but only behind a declared flag; nothing here needs that.)
- 2026-09-24 — **Four-way status, not three.** A reachable sibling whose slice simply has not been authored yet is neither `open` (nothing exists to be open) nor `cannot-determine` (the answer is known). It is `absent` — which is also exactly the found/not-found datum 1.26's banner would otherwise have derived in prose, so one vocabulary serves both consumers.
- 2026-09-24 — **Indeterminacy rides in the value, never the exit code.** `cmd_resolved` carries "cannot determine" as exit 2 because it answers one question about one run. These answer per repo, so a fixture with one `done` and one `cannot-determine` has no coherent process-wide code. Exit 0 always; the consumer reads the per-repo token. The "never a silent pass" contract is preserved by the token being explicit, not by the exit status.
- 2026-09-24 — **The resolvers report; they never decide.** `resolve-footprint` reports a divergence rather than repairing it; `slice-status` reports `absent`/`cannot-determine` rather than choosing an outcome. What to do about either belongs to a consumer — the `--fix` is 1.28's, the terminal disposition is 1.27's. That is what lets one pair of subcommands serve three consumers without encoding any one's policy.
- 2026-09-24 — **The front-matter parse is 1.25's, reused.** `repos:`/`work_item:`/`canonical_repo:` are declared and validated by 1.25; this spec calls that parser rather than writing a second one, per root CLAUDE.md's rule against re-implementing a check.

## Verification / evidence
`bash hooks/hooks.test.sh` green, with a case per criterion. Every fixture is purpose-built — this repo declares no siblings — and because board data arrives as flags, **every criterion here is provable offline**, with no live board and no disposition deferred to post-ship.
