## Problem
Nothing in flow can name a sibling repo or say which repos a work item touches. Before any reminder, gate, or scaffold can exist, the footprint has to be *writable* and *checkable* — a declared config surface for the standing relationship, declared front-matter for the per-item footprint, and one validator both the guard and `/flow:lint` call so the rule lives in one place (`flow-preflight.sh`, per CLAUDE.md).

Shipped means: a project can declare its siblings, a spec can declare its footprint, and a malformed or inconsistent declaration is caught on save.

## Value
As an engineer setting up a multi-repo project I want the footprint recorded in files the tooling validates so that a typo in a repo name fails on save instead of silently disabling every reminder downstream.

## Scope
**In:** `flow.repo_name` (this repo's handle) and `flow.related_repos` in the committed `.flow/config.yml` — `name` required, `project`/`repo`/`clone` optional. A gitignored `.flow/config.local.yml` override carrying `local_path` per sibling. Front-matter on a detail file: `repos:` (the footprint), `work_item:` (the join handle, **defaulting to `id:`**), `canonical_repo:`. A `flow-preflight.sh repos <spec>` subcommand — shape; every `repos:` name is `repo_name` or a declared sibling; `canonical_repo` is one of `repos:`. A `flow-spec-guard.sh` call when `repos:` is present. A `/flow:lint --specs` row. Scoping `flow-session-brief.sh`'s `project:`/`area:` match to the `ado:` block, so a sibling entry's `project:` cannot shadow the board coordinate. Docs + README.

**Out:** every consumer — banner (1.26), completion gate (1.27), authoring (1.28). ADO `repo:<name>` tag mirroring and its drift row (1.28). Any network fetch of `clone`. Reading a sibling's files — this subcommand is local-only.

## Acceptance criteria
- [x] `repos:` parses as a scalar split on `[`, `]`, `,` and whitespace — `repos: []`, `repos: [a]`, `repos: [a, b]`, and bare `repos: a` each yield the expected set — proven by four `hooks/hooks.test.sh` cases, reusing 1.22's `idlist` rule so the deferrals parser's entry detection stays untouched.
- [x] `repos` exits non-zero naming the offending token when a `repos:` name is neither `repo_name` nor a declared sibling, **and** exits non-zero naming `flow.repo_name` when `repos:` is present while the config declares none — proven by two harness cases. The second is the state of every repo today, so adopting `repos:` requires the config edit first, by design.
- [x] It exits non-zero when `canonical_repo:` is absent while `repos:` names more than this repo, and when it names a repo outside `repos:` — proven by two harness cases.
- [x] `repos` is clean on a file with no `work_item:` — the key defaults to `id:` and is not required — and exits non-zero when `work_item:` is present but empty — proven by two harness cases, so an ado spec needs no extra key and a blank one is not silently accepted.
- [x] `repos` exits non-zero when `local_path` appears under a sibling entry in the **committed** `.flow/config.yml`, and is clean when it appears in `.flow/config.local.yml` — proven by two harness cases, enforcing the gitignored-override Decision at save time. (Reading the value is 1.29's.)
- [x] `.flow/config.local.yml` is actually ignored — `commands/init.md` writes the `.gitignore` entry when it scaffolds the config, and `repos` warns when the file exists untracked-but-unignored — proven by a harness case plus inspection of the init step. Without this the validator only polices the committed file's *contents*, and the per-machine path Decision 1 exists to prevent gets committed in the sibling file instead.
- [x] `repos` reports an unknown key under a sibling entry rather than ignoring it, and does so without failing the save — proven by a harness case asserting exit 0 plus the message, **and** a guard case in hook mode asserting the guard relays it as a soft nudge. A preflight exit-0 stderr is dropped in hook mode, so without the relay the warning reaches nobody and a typo like `local-path:` silently disables verification anyway.
- [x] `flow-spec-guard.sh` rejects a malformed `repos:` block on save and is silent when the key is absent — proven by two harness cases.
- [x] A detail file carrying `repos:`, `deferrals:`, and `spawns:` yields the same parsed deferrals and the same spawn set as files carrying each alone, with the keys in any order — proven by harness cases over permuted fixtures.
- [x] A repo with no `related_repos` and a spec with no `repos:` produce the guard and session-brief output the harness already asserts literally — proven by a harness case in the existing `$BRIEF` assertion form, not by a diff against a pre-change build (which does not exist; see PRIOR ART in Decisions).
- [x] A populated `related_repos` whose entries carry `project:` does **not** change the session brief's ado coordinate — proven by a harness case on an **ado-mode fixture with no `SPECIFICATIONS.md`** (that branch runs only when the index is absent, `flow-session-brief.sh:43`), with a sibling `project:` placed **above** the `ado:` block, asserting the brief still reports the `ado:` block's own `project:`/`area:` (`flow.ado.*`, indented four spaces — there is no top-level `project:`). The awk matches `/^[[:space:]]*project:/` indentation-agnostically and keeps the first hit, so this is the regression that can actually happen; the fix scopes the match to the `ado:` block rather than anchoring it at column 0, which would break the real indented config.
- [x] The `/flow:lint --specs` row fires only when `repos:` is present — proven by inspection of the row's stated guard condition (`/flow:lint` is a model-executed prompt, so there is no bash-capturable output to diff).
- [x] Every documentation surface this format touches is updated in the same change — `README.md` (the config surface + the three front-matter keys, beside the existing `spec_filename` note at §What's in the box), `docs/guide.md` §2's spec front-matter template and §8 cheat sheet, `docs/how-it-works.md` §2's spec-model diagram, root `CLAUDE.md`'s `flow-preflight.sh` bullet (gains `repos` to its subcommand list), `hooks/CLAUDE.md` (a `repos` row in the subcommand table and a Rules bullet, mirroring the `spawns`/`blocking` entry), `commands/lint.md`'s `--specs` row table, `commands/init.md` (scaffolds the config surface + the `.gitignore` entry), and `skills/run/reference/authoring.md`'s detail-file template — proven by `grep -l -E 'related_repos|repos[:`]' ` over the eight named paths as operands, returning all eight. (`hooks/CLAUDE.md`'s subcommand row reads `repos <detail.md>` — a space, not a colon — so that file must also carry `repos:` or `related_repos` in its prose.)
- [x] `bash docs/mermaid.test.sh` is green after the §2 diagram edit — proven by running it (CI job `docs` runs it anyway; a bad block degrades silently on GitHub).

## Decisions
- 2026-09-24 — **`local_path` is gitignored, never committed.** `local_path: ../SIBLING` in a shared file is a per-machine path with no correct value to commit — it breaks for the next person. The committed config carries identity and coordinates (`name`/`project`/`repo`/`clone`); `.flow/config.local.yml` carries where *this* machine keeps the sibling. Absent → reminder-only, which still works.
- 2026-09-24 — **One validator, called by two consumers.** Per CLAUDE.md a machine-checkable rule lives in `flow-preflight.sh` and is never re-implemented inline; the guard and `/flow:lint` both call `repos`. This spec validates the declaration; **1.29** resolves it — `repos` never reads a sibling.
- 2026-09-24 — **Hook-consumed config in `.flow/config.yml` is deliberate — see 1.24's ADR amendment.** A reader of this spec alone sees bash (`flow-preflight.sh repos`, called by the guard) consuming the file 1.7 designated prompt-side. That boundary was amended in 1.24's D7, on the ground that `flow-session-brief.sh` has read the same file in bash since 1.19. Noted here so the reversal is not invisible from the spec that exercises it.
- 2026-09-24 — **`role:` dropped from the schema.** It was human-readable prose with no consumer in any member. Root CLAUDE.md forbids a config knob until a second real use exists; a `# comment` in the config serves the same purpose with no schema to validate.
- 2026-09-24 — **No baseline-diff criteria.** 1.22's Decision of 2026-09-02 settled that `hooks.test.sh` runs only the current tree, so "byte-identical to the pre-change build" is unfalsifiable. The null case uses the harness's existing literal-assertion form, and the real regression risk is the *populated* case (the session-brief `project:` collision), which now has its own criterion.
