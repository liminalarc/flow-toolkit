## Problem
Reminders (1.26) are advisory, so a multi-repo item can still reach a terminal state with slices unbuilt — the failure the whole design exists to prevent. Closing it needs a per-slice completion record readable from any repo, and a terminal step that consults it. 1.29 already answers "is that slice done"; what is missing is where ADO *records* a slice's completion, and what the done-step and `/flow:ship` do with an incomplete answer.

Shipped means: an item goes terminal only when every touched slice is done, and flow says which ones are not.

## Value
As an engineer finishing the last slice I want flow to confirm every other slice landed before the item closes so that a half-shipped item cannot be marked Done.

## Scope
**In:** the ADO completion record — a `slice-done:<name>` tag added to the card when a slice's run completes, one per repo, added atomically. (Flat-file needs no new record: each repo's own index already carries it, and 1.29 reads it.) The terminal disposition, consuming `flow-preflight.sh slice-status` (**owned by 1.29**, which resolves the ado answer from the `slice-done:` tags this spec writes, fed via its `--slice-done` input): **flat-file blocks** a local `DONE`, **ado refuses to propose** the transition and offers an explicit override — a **confirm-first prompt naming every missing slice and its repo**, proceeding only on explicit confirmation and recording the bypass in the spec's Decisions. Footprint names come from `resolve-footprint` (which honours `--tags`), so a tags-sourced footprint with no local `repos:` is never a pass. Every non-`done` value is outstanding: `open`, `absent` (a sibling slice nobody has authored — squarely the half-shipped case) and `cannot-determine` all hold the transition, each with its own message. Wired into `/flow:run`'s done-step — **fusing with 1.26's advisory reminder bullet rather than sitting beside it**, so §4 runs `slice-status` once and states one disposition — and into `/flow:ship`'s preflight as a **Class 3** row (judgment: ship can neither wait for nor fix a slice in another repo, exactly like the unreconciled-deferral row) that **blocks the release**. The override lives only in `/flow:run`'s done-step, not at ship time, so `ship.md`'s standing "⚠️ blocks" rule needs no amendment. In-Progress is idempotent — any repo's run may move the item there. A **write-capture double** for card writes (a stub `az` on `PATH` recording the calls it was asked to make), since 1.29's resolvers are read-only by design and cannot witness a write; this spec writes tags, so it owns the double.

**Out:** writing `System.Description` — see Decisions. New ADO schema fields. Reading sibling status or resolving footprints (1.29). Auto-ticking a sibling's slice from this repo. Any `slices:` front-matter map (ruled out by 1.24).

## Decisions
- 2026-09-24 — **Tags carry completion; flow never writes the card description.** The design brainstorm put a per-slice checklist in `System.Description`, and 1.24's Decision 4 called the description "neutral ground owned by neither repo" while explicitly delegating the carrier to this spec. That clause is **superseded here**: `System.Description` is HTML, so every tick would be a round-trip that can clobber human edits, against flow's propose-only, never-silently-overwrite stance with cards. `slice-done:<name>` tags share the footprint tags' read/write path, add atomically, cannot clobber, and are WIQL-queryable. A human-authored checklist may still exist; flow reads it and never writes it.
- 2026-09-24 — **Block in flat-file, steer in ado** (user decision). Flow owns the spec files and the local index, so refusing a local `DONE` is within its authority. The board owns the card, so ado gets a refusal-to-propose plus an explicit override rather than a hard block — the same propose-only boundary `implement.md` already draws for `System.State`. One rule, two dispositions, each matching who owns the artifact.
- 2026-09-25 — **The gate absorbs 1.26's reminder rather than sitting beside it.** 1.26 shipped an advisory §4 bullet that already runs `slice-status` and lists every non-`done` repo, ending "advisory here — it never blocks; 1.27 owns the terminal gate". Adding a second bullet would run the resolver twice and leave §4 saying both "never blocks" and "block" over the same data. 1.26's own Decision anticipated this — "a reminder that blocks is a gate with a worse error message" — so the two fuse: one invocation, one disposition.
- 2026-09-25 — **`absent` blocks.** 1.29 left the disposition to this spec. A sibling slice nobody has authored is the half-shipped case the Value story names, so it holds the transition exactly as `open` does — with its own message, since "not written yet" and "in progress" call for different human action.
- 2026-09-24 — **`cannot-determine` is never a silent pass.** Mirrors `cmd_resolved`'s settled contract and depends on 1.29 keeping its four-way vocabulary (`done`/`open`/`absent`/`cannot-determine`) rather than collapsing it.

## Verification / evidence
