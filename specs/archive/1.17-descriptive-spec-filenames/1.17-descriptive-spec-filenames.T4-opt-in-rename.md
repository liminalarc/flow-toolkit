## Goal
`/flow:lint --rename [<id>|--all]` — the migration any repo using the toolkit runs once,
on demand, to retrofit existing bare-id specs. Never runs unprompted; not part of `--fix`.

Flow: resolve each target's current path (`flow-preflight.sh spec-path`, T2) → read its
Title from the index (local) or `System.Title` (ado) → compute the slug (T3's rule) →
**present the full git-mv set and the index-link rewrites, then confirm** → `git mv` each
path (preserving history) and rewrite the index `[detail](…)` links in the same change.

Both shapes: a flat `specs/<id>.md` → `specs/<id>-<slug>.md`; a dir `specs/<id>/` → dir,
orchestrator, **and every task file** renamed together (a task's suffix comes from its own
`title:`). Archived specs are eligible but only when explicitly named or under `--all`.

Idempotent: an already-slugged spec reports "already migrated" and moves nothing. A target
whose slug would be empty stays bare. A rename that would collide is refused, not forced.

## Done when
- [ ] `--rename <id>` migrates one spec (both shapes) and rewrites its index link
- [ ] `--rename --all` migrates every active + archived spec in one confirmed batch
- [ ] Nothing moves before confirmation; the proposed set is shown in full
- [ ] `git mv` is used (history preserved), never delete+create
- [ ] Re-running is a no-op; a collision or empty slug is refused with a reason
- [ ] Dogfood: `--rename 1.17` renames `specs/1.17/` + all 5 task files + the index link,
      and `bash hooks/hooks.test.sh` is green afterward
- [ ] `commands/lint.md` documents the subcommand alongside `--fix`/`--migrate`

## Notes
Distinct from `--migrate` (flat → dir *shape* change). This changes *names* only. Say so in
the command doc so the two aren't confused.
