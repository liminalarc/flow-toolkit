## Problem
The valve only turns one way. Narrowing scope is rigorous and machine-gated: the deferral protocol makes you surface the cut, take a per-item decision, and record a `deferrals:` entry, and `flow-preflight.sh resolved` blocks `DONE` until every entry resolves. Widening — discovering mid-build that the spec is too small, mis-scoped, or simply wrong — has no protocol at all. `agents/flow-implementer.md:27` tells an implementer that discovering out-of-AC work means "stop and report it back… The orchestrator runs the deferral protocol; you do not" — but the deferral protocol covers narrowing only, so the instruction points at a procedure that does not handle this case. The orchestrator is left to widen silently or drop the work, and the only coverage is post-hoc: `agents/flow-verifier.md:21` notices "scope that widened beyond the task", and `skills/pr/reference/spec.md:10` flags creep once the diff exists.

Shipped means: a widening stops and asks, the same way a narrowing does, and the decision lands in the spec.

## Value
As an engineer mid-build I want a widening to stop and ask the same way a narrowing does, so scope grows by my decision and the reason survives in the spec rather than only in the diff.

## Scope
**In:** an amendment turn in `skills/run/reference/implement.md` §3, mirroring the deferral protocol's shape — surface what you would add and why, then take a per-item decision: **(a) amend this spec** (extend Scope, add the acceptance criterion, dated Decisions entry), **(b) re-home** to a new or existing spec, cross-linked both ways, or **(c) drop it**, with the reason recorded. A named destination for the implementer's existing report-back. One line in `skills/run/SKILL.md`'s Rules. Docs.

**Out:** an `amendments:` front-matter key, a `flow-preflight.sh` subcommand, a guard call, a `/flow:lint` row — see Decisions. Giving `PARTIAL` a producer, or retiring it — a separate decision (see Decisions).

## Acceptance criteria
- [ ] A widening surfaces **before** the added work is built, not after — proven by a scratch build in which the orchestrator hits out-of-AC work and stops with the decision prompt before any commit containing that work.
- [ ] Decision **(a)** lands the change in the spec — Scope extended, a new acceptance criterion added, and a dated Decisions entry naming what was added and why — proven by running it against a scratch spec and inspecting the three edits.
- [ ] Decision **(b)** cross-links both ways — the current spec's Decisions names what went where and why, and the receiving spec notes its origin in Problem or `links:` — proven by running it and inspecting both files.
- [ ] Decision **(c)** records the reason for dropping it in Decisions rather than leaving it only in the transcript — proven by running it and inspecting the entry.
- [ ] `agents/flow-implementer.md:27`'s report-back names the amendment turn for out-of-AC work, rather than the deferral protocol — proven by inspection of the edited line.
- [ ] A build in which nothing widens adds no step and emits no message — proven by a checkpoint build of an unchanged scratch spec producing output identical to today.

## Decisions
- 2026-09-02 — **Prompt-only: no front-matter key, no preflight subcommand, no guard, no lint row.** `deferrals:` earns its machinery because a narrowing can *silently lose promised scope*, which is why it gates `DONE`. An amendment adds — nothing is lost, and there is nothing to gate. Scope, the acceptance criteria, and Decisions already hold the record, and `/flow:pr` already flags unexplained additions. Building the symmetric machinery would be exactly the premature enforcement 1.2's **D1** declined ("no enforcement… revisit only if drift appears").
- 2026-09-02 — **`PARTIAL` stays out of scope, and may not want a producer at all.** It is validated in three hook files and counted at `hooks/flow-session-brief.sh:105`, but nothing in `skills/` or `commands/` ever sets it — the done-step writes only `DONE`. The tempting pairing (an amended spec ships partly, so mark it `PARTIAL`) does not hold: the deferral protocol makes `DONE` always reachable, since every unbuilt item is either built or re-homed, so a genuinely part-shipped terminal state never arises. That is why 22 specs have never needed it. The open question is whether `PARTIAL` should be **retired** (10 files, 2 hook regexes, 1 diagram) or given a distinct meaning such as "partly shipped, parked" — a real state that is neither `IN PROGRESS` nor `DONE`. Either way it is its own decision; bundling it here would make this two capabilities.

## Verification / evidence
Each criterion names its proof. The end-to-end evidence is a scratch build that hits out-of-AC work and is run once per decision branch — (a), (b), (c) — showing the record each one leaves. `bash hooks/hooks.test.sh` green (no hook logic changes here, so it must stay green rather than gain a case).
