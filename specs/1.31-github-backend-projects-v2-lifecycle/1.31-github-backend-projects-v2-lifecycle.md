## Problem
flow had two lifecycle authorities, `local` and `ado`. `liminalarc/atlas` tracks work on the org
Projects v2 board `liminalarc/projects/36`, which flow could neither read nor write: no way to
configure it, no index for `/flow:run`, and every ado-only path (archival trigger, pointer comment,
cross-repo tags, lint reconciliation, ship's DONE resolution) without a github counterpart.
`commands/init.md` already named `github-issues` as the next adapter. Shipped = a repo whose
backlog is board 36 runs the full loop with no local index.

## Value
As an engineer whose team tracks work on a GitHub Projects board, I want flow to treat that board
as the index so that I get the same spec-driven loop — and the same DONE gates — without
maintaining a second backlog.

## Scope
**In:** `lifecycle_authority: github`; config + `/flow:init --backend github` with column discovery;
the `gh` ladder incl. the `project` scope gap; the Status field as `state_map`; repo-qualified ids;
the run path (board read, Status write, `Spec:` comment, terminal-column archival, `--add`);
cross-repo `repo:`/`slice-done:` labels; session-brief orientation; `/flow:lint` reconciliation +
drift; `/flow:ship` DONE resolution; a programmable `gh` stub; the board 36 walk; docs + ADR.
**Out:** labels as a *status* carrier; any board write beyond the Status field, one comment, the
cross-repo labels and item creation; an MCP rung; jira; behavior changes to `local`/`ado` beyond
generalizing shared prose.
**Precondition:** the `gh` token carries `project` scope before T1. An org policy refusing the grant
blocks this spec and is surfaced, never worked around.

## Acceptance criteria
- [ ] `/flow:init --backend github` writes the config, creates `specs/`, writes no
      `SPECIFICATIONS.md` — `grep` on the config plus `test ! -f`.
- [ ] `state_map` is discovered **and used** — the stub answers `field-list` with
      `Icebox`/`Cooking`/`Shipped`; the written `state_map` keys equal exactly those three.
- [ ] A missing `project` scope stops init with `gh auth refresh -s project` and writes no config —
      stub returns gh's scope error.
- [ ] `<repo>-<issue#>` ids resolve flat, in directory form and archived — `hooks.test.sh` cases on
      a dash-containing `my-app-2-42`.
- [ ] An item in a mapped column resolves to its token — one stubbed item per column.
- [ ] A closed issue with `state_reason: not_planned` resolves `SUPERSEDED` — stub case.
- [ ] An item in no column, or an unmapped one, reports the literal `unmapped` and gets no token.
- [ ] Open items group by column — stubbed multi-column `item-list`: one header per mapped column,
      no ungrouped item.
- [ ] An empty result states the query ran rather than implying an empty backlog — stub case.
- [ ] The listing carries an explicit `--limit` or `--query` — stub returns 45 items, all 45
      accounted for.
- [ ] `/flow:run <repo>-<n>` authors `specs/<repo>-<n>-<slug>.md`, slug from the issue title — the
      spec guard passes on the authored file.
- [ ] `--add` creates the issue, boards it, sets the initial column, adopts `<repo>-<n>` — stub argv
      log in a github-mode scratch repo (no second live board: that would need its own grant).
- [ ] Exactly one Status mutation reaches the board, on the item resolved from the issue — one
      `item-edit` in the argv log. (Stated as the outcome, not a flag set: `--url`/`--field`/
      `--value` is what gh 2.103.3 documents, but the AC should not freeze a CLI surface.)
- [ ] The pointer comment is found by its `Spec:` marker and edited, never duplicated — stub whose
      last comment is a human's: the edit targets the pointer's id, the human comment is untouched.
- [ ] **Offline**, the write boundary holds in cardinality and identity — one `item-edit`, one
      comment edit, (cross-repo) one `slice-done:` add, no other mutating argv, every mutating id
      among the stub's canned ids.
- [ ] **On the live walk**, item safety rests on confirm-first proposal, not on argv — the stub has
      no pass-through, so nothing captures calls against the real board. Stated plainly rather than
      claimed: every board 36 mutation is shown and confirmed before it is sent.
- [ ] No `mcp__*` board write occurs — transcript-asserted.
- [ ] A `gh` **failure** is announced and flow stops and reports — stub exits non-zero.
- [ ] A `gh` **absence** is announced and flow stops and reports — a PATH with no `gh` at all; a
      PATH-first stub cannot simulate its own absence, so this needs its own case.
- [ ] The session brief prints `flow-toolkit: github backend — <owner> · project <n> — …`, exits 0,
      makes no network call — `hooks.test.sh` cases for the line, a shadowed sibling key, a missing
      `project_number`, a non-github fall-through, and a **poisoned `gh` first on `PATH` that fails
      the case if invoked**; suite green.
- [ ] Cross-repo runs on label-derived tags — a scratch fixture whose issue carries `repo:a repo:b`
      renders the expected `resolve-footprint`/`slice-status` output and adds one `slice-done:`.
- [ ] `/flow:lint` flags a detail file whose issue reached a terminal column outside flow and offers
      the `git mv` confirm-first — stubbed fixture in a github-mode scratch repo.
- [ ] An unreachable board reports *not evaluated*, never a pass — same fixture, stub non-zero.
- [ ] `/flow:lint --fix` re-syncs `repo:` labels only — the expected add and remove are present and
      no `slice-done:` label is touched.
- [ ] `/flow:ship --dry-run` resolves the DONE set from the board and blocks on an unresolved
      deferral **and** on a non-`done` slice — asserted by preflight class and outcome per case.
- [ ] The board 36 walk runs end-to-end: one `flow-test` issue goes run → IN PROGRESS → DONE →
      archived → exactly one pointer comment, recorded as a pass/fail checklist in Verification.
- [ ] Docs land together — `grep -l` for the literal `lifecycle_authority: github` or
      `--backend github` returns all five of `README.md`, `docs/guide.md`, `docs/how-it-works.md`,
      `docs/architecture.md`, `commands/help.md`; `bash docs/mermaid.test.sh` green.

## Decisions
- 2026-11-18 — Token is `lifecycle_authority: github`; the adapter is `github-issues` in prose, per
  `commands/init.md`'s existing forward reference.
- 2026-11-18 — **Status field, not labels.** Board 36's columns are what the team moves; a parallel
  `status:*` label set would drift from them and duplicate a state the board already owns.
- 2026-11-18 — Ids are **always** repo-qualified `<repo>-<n>`. Issue numbers are unique per repo
  only and an org board can gain a repo at any time, so qualifying unconditionally means no id ever
  changes. Parsed as *last dash-delimited numeric segment* — applied to `id:`, never to a filename.
- 2026-11-18 — Labels keep one job: the cross-repo `repo:`/`slice-done:` tags, which Projects v2 has
  no field equivalent for. The 1.29 resolvers take tags as input, so no hook gains a query.
- 2026-11-18 — The ladder is **`gh`-only**. The first draft's "announced MCP fallback" named no
  server and an unnamed rung cannot be tested; a `gh` failure stops and reports.
- 2026-11-18 — **Board 36 read (token scope granted).** Status options are
  `Discovery · Backlog · Ready for Dev · In Dev · Dev Done · Ready for Review · Deployed` — nothing
  like GitHub's defaults, which retires the "a hardcoded map passes vacuously" risk on this board in
  practice. 17 items, all from `liminalarc/atlas`; none has ever reached a terminal column, so the
  archive trigger is unexercised live. `state_map` mirrors ado's category mapping per the user:
  pre-dev (`Discovery`, `Backlog`, `Ready for Dev`) → `NOT STARTED`; in flight (`In Dev`,
  `Dev Done`, `Ready for Review`) → `IN PROGRESS` (ado maps `Resolved` the same way); `Deployed` →
  `DONE`; closed `not_planned` → `SUPERSEDED`. Single-repo today, so the unconditional `atlas-12`
  qualifier is insurance against a second repo joining, not a present need.
- 2026-11-18 — Three `gh` facts checked against `--help` (gh **2.103.3**) before the ACs were
  written — a later round disputed the first from recall and was wrong, so the version is pinned:
  `item-edit`
  selects by issue `--url` and permits one field value per invocation on a non-draft issue (a
  guarantee to lean on, not re-assert); `item-list` defaults to `--limit 30`, so an unscoped listing
  silently truncates; `issue comment --edit-last` edits the user's last comment *whatever it is*, so
  the pointer must be found by its `Spec:` marker or flow would overwrite a human's comment.
- 2026-11-18 — **The `gh` stub is programmable, unlike 1.27's `az` double**, which is documented as
  "exits 0 and prints nothing" because ADO writes need no return value. Five criteria here need the
  stub to *answer* — canned `field-list` options, a scope error, stubbed items, a comment list — and
  a write is only reached after a read resolves the item. So it logs argv **and** serves scripted
  stdout + exit status per invocation. It stays a fixture: no preflight subcommand gains a call.
- 2026-11-18 — **One spec, and nothing deferred out of it.** Two independent review rounds called
  INVEST-Small WEAK. Round 1's read/write seam was withdrawn by its own author (a read-only backend
  can't carry a project whose backlog *is* the board). Round 3 reached the finding on a narrower
  basis — that the spec pre-named T4 as a deferral candidate, which by definition makes it
  separable. That basis is now removed rather than argued: **all six tasks land here**, T4 included,
  with no pre-authorised deferral. Sequencing still applies — T1-T3 must be independently green and
  committable before T4 starts — but as build order, not as an escape hatch.
- 2026-11-18 — Round 2 offered "ado's base backend was itself one spec" as precedent for the size.
  **Not used:** nothing in `SPECIFICATIONS.md`'s archive (1.1-1.30) introduces the ado backend — it
  predates this backlog — so the claim is unverifiable from this repo and carries no weight here.
- 2026-11-18 — **Live board for the walk, stub for the writes.** 1.18 shipped ado
  "specified-but-unexercised, field-verified after"; 1.27 added the capture double so writes are
  asserted offline. Both apply: board 36 proves the round-trip, the stub proves the boundary in CI.
  "No non-`flow-test` item modified" is not falsifiable on a board colleagues edit concurrently, so
  it is proven by argv identity instead of board state.
- 2026-11-18 — **Backend-branching enumeration (T1's gate, measured not assumed).** `grep` over all
  five hooks: `lifecycle_authority` appears **once**, in `flow-session-brief.sh`. `flow-preflight.sh`
  reads only `flow.repo_name`/`flow.related_repos` from the config and contains no `ado:`,
  `state_map` or `project_number` reference; the spec, claude and commit guards read no config at
  all. So the github backend needs **no** preflight or guard change — the `--done`/`--tags`/
  `--slice-done` input design (1.27, 1.29) is exactly what makes a third backend free at the hook
  layer. T2 and T4 build on this rather than on an assumption.
- 2026-11-18 — **The terminal column CLOSES the issue, via the board's own automation.** Observed on
  the live walk: setting #51's Status to `Deployed` flipped the issue `OPEN`→`CLOSED` with
  `stateReason: COMPLETED`, though flow issued exactly one `item-edit` and no close. Every other
  field (labels, milestone, assignees, title) was byte-identical, so flow's write boundary held —
  but "flow never closes an item" is wrong as a *claim about effects*. The propose-first prompt must
  therefore say that confirming the terminal transition will also close the issue on a board with
  the default workflow. A closed+`COMPLETED` issue maps to `DONE`, so the archival rule is unchanged.
- 2026-11-18 — **Teardown: remove the board item first, then the issue.** Deleting the issue first
  strands its project row with null content until GitHub reaps it (minutes, not never). `item-delete`
  **succeeds on an item that still has content** — the second walk removed its row cleanly and the
  board returned to 17/0 orphans immediately — but was denied on the already-orphaned rows from the
  first walk. So the ordering is the fix, and it is available; reversing it leaves a window that
  cannot then be closed.
- 2026-11-18 — **A PATH-first stub is skipped by a Windows-form `PATH` entry.** Building `PATH`
  from `C:/...` instead of `/c/...` left the real `gh` first, so an AC3 run queried the **live
  board** and reported exit 0 while appearing to pass. Git Bash resolves only POSIX-form entries.
  Every prompt-path verification therefore asserts `which gh` resolves inside `gh-stub` before it
  trusts a result; without that guard a verification can silently grade the wrong system.
- 2026-11-18 — **The auto-close fires on the terminal column only.** The second walk set `In Dev`
  first: the issue stayed `OPEN`. Only `Deployed` flipped it to `CLOSED`/`COMPLETED`. So the
  disclosure belongs on the terminal transition alone, not on every Status write.
- 2026-11-18 — **`gh project item-list` lags its own writes.** An item added and confirmed present
  by a direct GraphQL node query was still absent from `item-list` moments later. Flow must not read
  a just-added item's absence from a listing as a failed add.
- 2026-11-18 — Two further live facts: `gh project item-add` lands an item in the board's **default
  column** (`Backlog` here), not a null status — so `--add` must still set the initial column
  explicitly rather than assume; and `gh api` endpoints must be passed **without a leading slash**
  (`repos/o/r/...`), because Git Bash rewrites `/repos/...` into a filesystem path and gh rejects it.
  The pointer-comment refresh uses `gh api --method PATCH repos/<o>/<r>/issues/comments/<id>` — gh
  has no edit-comment-by-id command, and `--edit-last` is forbidden for the reason already recorded.
- 2026-11-18 — The root CLAUDE.md line cap is not an AC: `flow-claude-guard.sh` enforces it on every
  save, and a rule lives in exactly one place.
