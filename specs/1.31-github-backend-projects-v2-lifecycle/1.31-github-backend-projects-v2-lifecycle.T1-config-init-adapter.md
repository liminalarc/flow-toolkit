## Goal
Define the `github` backend's config schema in one place, teach `/flow:init --backend github` to
fill it by introspecting the board (the `discover_config()` pattern `commands/init.md` already names
for this adapter), and settle up front which parts of the hook layer assume local-or-ado — so no
later task builds on a guess.

## Done when
- [ ] The schema is documented once (`skills/run/SKILL.md`'s backend block) and referenced, not
      restated, by `commands/init.md`: `owner`, `project_number`, `status_field`, `state_map`
      (column → canonical token), optional `repo` filter. The board's org may differ from the git
      remote's, as in ado.
- [ ] `/flow:init --backend github` calls `gh project field-list <n> --owner <org>` and proposes the
      `state_map` from the board's actual single-select options, confirm-first; an option it cannot
      map is surfaced for the user to assign rather than dropped. The capture double records that
      call happening before any config write.
- [ ] A missing `project` scope is caught here first, reported as `gh auth refresh -s project`, and
      init **stops** — no config file is written.
- [ ] It creates `specs/` and writes no `SPECIFICATIONS.md`.
- [ ] The id rule is stated once: `<repo>-<issue#>`, parsed as *last dash-delimited numeric segment
      is the issue number*, applied to the front-matter `id:` value and **never** to a filename
      (1.17's identity rule), so repo names containing dashes stay unambiguous.
- [ ] A written enumeration lands in the spec's Decisions: which `flow-preflight.sh` subcommands and
      which guards actually branch on backend today, and therefore whether anything beyond the
      session brief needs changing. T2-T4 build on that answer rather than assuming it.

## Notes
Mirror the ado block's shape so the three backends read as one table, not three dialects.
