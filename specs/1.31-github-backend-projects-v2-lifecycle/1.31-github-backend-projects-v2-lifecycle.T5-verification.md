## Goal
Two substrates, each proving what the other cannot: a `gh` write-capture double makes the write
boundary assertable offline and in CI, and a bounded walk on live board 36 proves the real
round-trip. Reads run against the whole board; every write targets a designated item.

## Done when
- [ ] `hooks/fixtures/gh-stub/gh` exists: first on `PATH`, `FLOW_GH_CAPTURE_LOG` set, every `gh`
      call recorded with full argv instead of executed — **and** able to answer, serving scripted
      stdout and exit status per invocation (`FLOW_GH_STUB_DIR` of canned responses keyed by
      subcommand, with `FLOW_GH_STUB_EXIT` for the failure paths). 1.27's `az` double only logs,
      because ADO writes need no return value; here `field-list`, `item-list`, `issue view` and the
      scope-error paths all have to return something, and a write is only reached after a read
      resolves the item. Documented in `hooks/CLAUDE.md` beside the `az` double.
- [ ] The seeding step captures the designated item/issue ids as a list, so the write assertions can
      check **identity**, not just how many calls were made.
- [ ] Stub assertions cover the write boundary: exactly one `item-edit`, exactly one comment edit,
      exactly one `slice-done:` label add on the cross-repo path, no other mutating argv, and every
      mutating call's id inside the designated set.
- [ ] The transcript shows no `mcp__*` board write — an MCP call bypasses `PATH`, so the stub alone
      cannot witness the likeliest violation (1.28).
- [ ] The scope-gap and `gh`-failure paths are exercised with the double returning gh's scope error
      and a non-zero exit, asserting the actionable message and the stop-and-report.
- [ ] 3-5 `flow-test`-labelled issues on board 36 are designated or created (one per `state_map`
      column, one closed `not_planned`, one carrying `repo:` labels). Teardown documented.
- [ ] A scratch clone is `/flow:init --backend github`'d against board 36 and the generated
      `state_map` matches the board's real columns.
- [ ] One `flow-test` issue goes end-to-end: `/flow:run <repo>-<n>` → spec authored → IN PROGRESS
      column → DONE → detail archived → exactly one pointer comment.
- [ ] A pass/fail checklist per orchestrator AC is recorded in the orchestrator's Verification
      section, naming which substrate proved each one.

## Notes
Confirm with the user before the first write to board 36 — it is a live team board, not a fixture.
Item-safety is proven by argv, not by board diff: on a board colleagues edit concurrently, a diff
cannot attribute a change to flow.
