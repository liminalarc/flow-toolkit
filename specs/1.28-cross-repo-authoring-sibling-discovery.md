## Problem
1.25 makes the footprint writable, but only by hand: an engineer has to know the front-matter keys, write a slice file per repo, keep the cross-pointers consistent, and in ado mode tag the card. Every one is a step a human will skip, and a skipped step disables the reminders and the gate silently. Authoring has to produce a correct footprint by default, and `/flow:init` has to declare siblings without hand-editing config.

Shipped means: `--add` on a multi-repo item produces every slice and the card tags, and `/flow:init` can populate `related_repos`.

## Value
As an engineer capturing a cross-repo item I want `--add` to produce the slices, pointers, and tags so that the footprint is right the first time rather than correct only when I remember all four keys — and, once per project, to declare my siblings without editing YAML by hand.

## Scope
**In:** `/flow:run --add` asks which repos the item touches (only when `related_repos` is declared), then writes `repos:`, `work_item:`, and `canonical_repo:` into each slice, scaffolding the per-repo detail file where the sibling is reachable **and flow-managed in the same backend**, and emitting copy-paste instructions otherwise. `/flow:init` offers to populate `related_repos` — discovered from the board's projects in ado mode, asked in local — and suggests the symmetric entry for the sibling, **including on `--adopt` against a repo configured before cross-repo existed**. The **adoption path**, consuming 1.29's `undeclared:`/`undeclared-self:` report: `/flow:lint` reports them and offers to write the entries confirm-first; `--add` offers to bootstrap `related_repos` when you name a repo the config does not know, instead of silently skipping the footprint question; `flow-session-brief.sh` gains one nudge toward `/flow:lint` when a **local** spec file names an undeclared repo. 1.25's block message is re-pointed at `/flow:init --adopt` so the hard stop routes somewhere. ado only: write the `repo:<name>` tag mirror on authoring, and a `/flow:lint` drift row that **reports** `flow-preflight.sh resolve-footprint`'s divergence (**detection owned by 1.29**) with a **confirm-first** `--fix` that re-syncs tags **from** front-matter.

**Out:** detecting the divergence or the undeclared repos itself (1.29). Any session-brief read of a board — the nudge is local-file-only, per 1.19's standing rule that the brief never queries a board or the network. Cloning or opening a sibling — instructions only. Scaffolding into a repo flow cannot reach, or one on a different backend. Writing anything but the new slice file and its index line into a sibling. Completion tags (`slice-done:`, owned by 1.27).

## Acceptance criteria
- [ ] `--add` in a repo with no `related_repos` asks no footprint question and adds no cross-repo artifact — proven by structural assertions, not a baseline diff: the written front-matter carries none of `repos:`/`work_item:`/`canonical_repo:`, the index gains exactly one line, `flow-preflight.sh repos` is clean, and the transcript shows no footprint prompt.
- [ ] `--add` on a two-repo item writes two slice files with exactly one `canonical_repo` equal to its own `repo_name`, identical `work_item:` values, and identical `repos:` sets across both trees — proven by asserting those three equalities across the fixture pair, plus `flow-preflight.sh repos` clean on each file.
- [ ] The same holds at N=3 — proven by a three-repo fixture; 1.26 asserts the >2 case separately for the same reason, so N=2 alone is not evidence.
- [ ] An unreachable sibling, a non-flow directory, and a sibling on a different backend each yield copy-paste instructions and leave no partial write in either repo — proven by three scratch runs asserting both trees' `git status`.
- [ ] Scaffolding a sibling **creates** the slice file at a path that did not exist and appends **exactly one** line to the sibling's index, with no other line in that file changed and **no other path in the sibling tree touched** — proven by asserting the sibling's `git status` names exactly those two paths and the detail file is a new path, not an overwrite.
- [ ] A reachable, same-backend sibling is **not** scaffolded when the human declines — proven by a scratch run answering no, asserting both trees' `git status` clean. This and the criterion above are what fence all four clauses of 1.24's write exception.
- [ ] The sibling's slice id is allocated from the **sibling's** index, not copied from this repo's, and equals the next free `Spec` number in the sibling's **highest existing phase** — proven by a fixture whose sibling already uses this repo's id for an unrelated spec, asserting the one expected id and that the slices are joined only by `work_item:`.
- [ ] `/flow:init` populates `related_repos` on sign-off and never without it — proven by a scratch init run declined and then accepted.
- [ ] In ado mode `/flow:init` discovers candidate siblings from the board's projects, MCP-first with the `az` fallback and the prompt-and-paste last resort `commands/init.md` already mandates — proven by a scratch run per branch, asserting the discovery path taken and that a failure never silently yields an empty list.
- [ ] It suggests the symmetric entry for the sibling rather than only this repo's half — proven by inspecting the emitted suggestion against the sibling's own `related_repos` shape.
- [ ] No board call is made in local mode — proven by local-mode scratch runs of `--add`, `/flow:init` and `/flow:lint`, asserting no `az`/network invocation via a stub on `PATH`.
- [ ] In ado mode, the card's `repo:` tag set after authoring equals the front-matter `repos:` set — proven against **1.27's write-capture double** (1.29's resolvers are read-only and cannot witness a write), asserting the recorded call set. **Disposition:** the real board round-trip ships specified-but-unexercised and is field-verified on the Pipeline Toolkit project after release, per 1.18's precedent.
- [ ] The drift row reports 1.29's `divergence:` line for a card whose tags name a repo the front-matter omits — proven offline by feeding 1.29's `--tags` input.
- [ ] `--fix` re-syncs so the card's tag set equals the front-matter `repos:` set while the front-matter is unchanged — proven against 1.27's write-capture double, asserting both halves so a `--fix` that did nothing fails. **Disposition:** as AC10, the real board write is field-verified after release.

## Decisions
- 2026-09-24 — **Scaffolding a sibling is the one sanctioned cross-repo write, and 1.24's Decision 3 carries the exception explicitly.** It is bounded to *creating* a new slice file and *appending* one index line, never editing existing content, and only in the turn the human asks. AC5 is what proves the bound; the ADR's D7 states it, so the record and the behavior agree on day one.
- 2026-09-24 — **The sibling's id is allocated from the sibling's index, never copied.** 1.24 ratified that each repo assigns its own `Phase.Spec` numbers from its own backlog — that is precisely why `work_item:` exists as a separate join key. Copying this repo's id would collide with whatever the sibling already numbered that way. The slices share a `work_item:`, not an id.
- 2026-09-24 — **Scaffolding requires the same backend; otherwise instructions.** An ado-backed sibling has no index to append to, and writing one would mean a second card — ruled out by 1.24. A non-flow directory has nothing to append to at all. Both degrade to copy-paste rather than guessing.
- 2026-09-25 — **The brief nudges from local files only; it never reads a board to find an undeclared repo.** The strongest adoption signal is an ado card whose `repo:` tags name repos the config lacks — and the brief cannot see it. 1.19 made that a standing rule (`docs/guide.md`: the brief "never queries a board or the network", because it runs at every session start in every project), and spending a board round-trip per session to catch a once-per-repo setup gap is a bad trade. The brief fires on the weaker local signal; `/flow:lint`, which already queries the board by design, catches the tag case.
- 2026-09-25 — **Detection reports, the asking is conversational, and nothing writes config unprompted.** `/flow:lint --fix` already re-syncs *tags* from front-matter without asking, because front-matter is the ratified authority and the tags are a derived mirror. Config is different: `related_repos` is a human's statement about how their project is laid out, and flow has no authority to infer it. Every entry is written confirm-first, on all four surfaces.
- 2026-09-24 — **`--fix` re-syncs tags from front-matter, never the reverse, and asks first.** 1.24 ratified front-matter as the portable authority; a fix writing the other direction would let a stray board tag rewrite the record. The direction is not the only question: this is a new class of lint write — a *board* mutation — and 1.18 settled that when `/flow:lint` acts on a board query it "offers the move **confirm-first**; never moves unprompted". Nothing about a tag re-sync makes it safer than the move 1.18 gated, so it adopts the same confirm-first shape rather than claiming an exemption.
- 2026-09-24 — **No baseline-diff criteria.** 1.22's Decision of 2026-09-02 retired "byte-identical to the pre-change build" as unfalsifiable, and sibling 1.25 re-ratified it as a standing rule. The first draft of AC1 re-litigated it; it now asserts structure — which keys are absent, how many index lines were added, `repos` clean — which is falsifiable against generated prose.

## Verification / evidence
Scratch two-repo and three-repo fixtures for the authoring paths, plus one whose sibling already uses this repo's id for an unrelated spec (the id-allocation case), and three unreachable-sibling variants. A scratch init run for discovery. The ado paths run against 1.29's recorded-tag stand-in, with the one live-board criterion carrying an explicit disposition above. `flow-preflight.sh repos` clean on every generated slice is the machine check that authoring and validation agree.
