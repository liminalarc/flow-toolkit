## Problem
Flow's unit of work assumes one repo. A project whose work items cross repos has no way to say so: the index names an item, the detail file describes it, and flow sees only the repo it is standing in. Origin: the Pipeline Toolkit project, where one board card routinely spans a toolkit repo and a tamper-isolated state repo; it generalizes to the ordinary front-end/back-end card. Today the human holds the whole footprint in their head — which repos a card touches, which slice this run builds, which siblings remain — and flow will walk an item to Done with half of it unbuilt.

Shipped means: the cross-repo model is ratified and the group implementing it is declared and ordered. The capability lands in 1.25–1.29.

## Value
As an engineer whose project spans repos I want flow to know a work item's full footprint so that I orchestrate the slices from a record rather than from memory.

## Scope
**In:** the cross-repo model — one work item → one canonical spec + N repo slices, joined by `work_item:`; the read/write boundary and its one bounded exception; the config-surface reversal; and a `spawns:` set (1.25 declaration, **1.29 resolvers**, 1.26 awareness, 1.27 completion, 1.28 authoring + discovery). A **D7** entry in `docs/architecture.md`, since that file is where this repo's ratified decisions live and this spec's only deliverable is ratified decisions.

**Out:** every implementation (owned by the members). Cross-repo *execution*, ever — flow never checks out or builds a sibling, and writes one only under the bounded exception in Decisions. A second card per repo. Read-only `clone` fetch of an un-checked-out sibling (a follow-up, not a member). The **completion carrier** — 1.24 ratifies that per-slice completion exists and is per-backend; *which* ADO artifact carries it is 1.27's decision.

## Decisions
- 2026-09-24 — **One work item, N slices — never a second card per repo.** A card per repo doubles the backlog and splits one acceptance criterion across items that drift independently. The item is the unit; the repo is an attribute of where its work lands.
- 2026-09-24 — **`work_item:` is the join key; the id is not.** In flat-file mode each repo assigns its own `Phase.Spec` numbers from its own backlog, so repo A's `1.24` and repo B's `1.24` are unrelated specs — "run the same id in the sibling" would open the wrong thing. ADO hides this because a card number is globally unique by construction. So each slice keeps its own local `id:` and its own index entry, and a `work_item:` handle joins them. It **defaults to `id:`**, which makes ado mode need no extra key at all and lets both backends converge instead of forking. `canonical_repo:` (not a `canonical: true` boolean) names which repo holds the full spec — a slice can then check "is it one of my `repos:`?" and "am I it?" without reading a sibling; a boolean could not be verified as unique without cross-repo access.
- 2026-09-24 — **Flow may read a sibling. Flow writes one only to create a new slice.** The motivating sibling is a tamper-isolated state store, and that isolation is on the *write* path — a read costs it nothing. This replaces "awareness only", which was too strong to implement: flat-file mode has no write-free way to know a sibling's state (see below), so forbidding reads would have left the completion gate unbuildable. The **one bounded exception** is ratified in 1.28: when the human asks for it in that turn, `--add` may create a new slice detail file in a sibling and append one line to its index — never edit existing content, never touch any other file, and never without that turn's request. Everything else stays read-only. Each slice is still a separate, human-initiated run and a separate PR; the human stays the orchestrator.
- 2026-09-24 — **Per-repo indexes aggregate; no `slices:` front-matter map.** The design brainstorm proposed a `slices: {toolkit: done, …}` map in the canonical spec. Two faults. It is a second copy of a fact each repo's index already owns, in a detail file that is forbidden to carry status. And the canonical spec lives in *one* repo, so a sibling ticking its own slice would have to write into another repo's files — the cross-repo write just ruled out. Instead each repo records its slice in its own index, exactly as it records every other spec, and completeness is read by aggregating them. In ado mode the **card** is neutral ground owned by neither repo, so no cross-repo access arises at all — *which* card artifact carries it is delegated to 1.27, which chose `slice-done:<name>` tags over a description checklist (the description is HTML, and a round-trip on every tick can clobber human edits). The repos are *related*, not merged: work in either is usually local to it, and this keeps the common case untouched.
- 2026-09-24 — **In ado mode the `repo:<name>` tags are load-bearing, not decoration.** The brainstorm called them a board-visible convenience, but a card exists before any repo holds a spec file for it — so on first open in a second repo there is no front-matter to read and the card is the only possible source of the footprint. Tags carry it: a set, structured, WIQL-queryable, readable with no local file. Precedence is unchanged — front-matter wins wherever a local slice exists, tags are the source only where none does, and `/flow:lint --fix` re-syncs tags **from** front-matter, never the reverse. Completion state is separate data with a separate lifetime; its carrier is 1.27's decision.
- 2026-09-24 — **`clone` is reminder text, never fetched.** Verification only matters to someone about to work in the sibling, and that person has it checked out — a fetch spends auth, latency, and a cache to answer a question only for people who cannot act on it yet. `local_path` covers the day-one case. Since verification is optional and non-fatal either way, adding a fetch later changes no contract.
- 2026-09-24 — **Spawned as a group, not one spec.** Capabilities that ship and fail independently: a declared format, its resolvers, a reminder, a completion gate, an authoring flow. Bundled, INVEST Small fails and nothing lands until all of it does. 1.28 depends only on 1.29, so it runs parallel to 1.26/1.27.
- 2026-09-24 — **The group splits by mechanism, not by user-facing moment — 1.29 owns the shared resolvers.** The first decomposition split on *when the human sees something* (declare / remind / gate / author). Three independent spec reviews each found the same consequence: footprint resolution (front-matter, else ado tags, plus the divergence report) was claimed by both 1.26 and 1.28, and sibling slice status (`local_path` → the sibling's index, keyed by `work_item:`) by both 1.26 and 1.27 — with no owner declared in any Scope. Worse, 1.26 was ordered *before* 1.27, so it would have built a prose reader that 1.27 then replaced in bash: rework ordered in by construction. Both are machine-checkable invariants, so root CLAUDE.md puts them in `flow-preflight.sh` and forbids a second inline implementation. 1.29 owns both as subcommands; 1.26, 1.27, and 1.28 consume them. Ids carry no order in a spawn set — `after:` does — so adding 1.29 needed no renumbering.
- 2026-09-24 — **`related_repos` lives in `.flow/config.yml`, amending 1.7's prompt-side/hook-side split.** 1.7 ratified `.flow/config.yml` as flow's backend config and `.flow-toolkit.json` as the hook-side one. That boundary has already moved: `flow-session-brief.sh:43-53` has read `.flow/config.yml` in bash since 1.19, so "the prompt side" is no longer bash-free. The footprint is backend configuration in every sense that matters to a reader, and splitting it across two files to preserve a boundary that no longer holds would cost more than it buys. **1.17's placement of `spec_filename` is untouched** — its rationale was per-knob ("nothing in bash consumes *it*") and still true, since the guards read no filename knob. Recorded here rather than in 1.25 because amending a ratified decision belongs in the ADR.
- 2026-09-24 — **Docs land per member, never as a trailing docs spec.** CLAUDE.md requires commands, hooks, and README to change *together*, so each member carries its own documentation criterion naming the exact files it touches. A group-wide docs spec at the end would leave every intermediate member shippable-but-undocumented, which is the failure that rule exists to prevent.
- 2026-09-24 — **This repo cannot dogfood it.** flow-toolkit is single-repo, so evidence is purpose-built `hooks/hooks.test.sh` fixtures plus the Pipeline Toolkit project as day-one user post-ship — the arrangement 1.22 used.
